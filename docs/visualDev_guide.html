Référence technique centrale

Ce guide rassemble le fonctionnement architectural, le pilotage via hubctl, et le développement avec le template d'application. Valable pour la version de parc 0.45.x / Hub 3.38.x — les fichiers VERSION font foi. Version textuelle complète : guide-parc-poulidor.md.

1. Architecture globale et Flux

Le parc POULIDOR est composé d'un cerveau central (le Hub) et d'une multitude d'applications métier satellites (issues du Template). Le Hub lui-même est une stack Docker de 4 services :

dbhub-dbPostgreSQL 16 « hub_auth » (~36 tables)
hub-apihub-apiFastAPI — 21 routeurs : SSO, registre d'apps, M2M/OIDC, messagerie SSE, backups/snapshots, audit, VPN
hub-frontendhub-frontendNginx — SPA vanilla JS + console admin, terminaison TLS
wireguard-serverhub-wireguardVPN WireGuard (profil compose — démarré seulement si activé)

Le flux SSO — le mot de passe ne quitte jamais le Hub

sequenceDiagram
    autonumber
    actor U as Utilisateur
    participant N as Navigateur / SPA
    participant H as Hub (hub-api)
    participant A as App (backend FastAPI)
    U->>N: ouvre l'app
    N->>H: POST /api/auth/login (identifiants)
    Note over H: émet un JWT signé RS256
avec sa clé PRIVÉE
    H-->>N: JWT (30 min) + refresh token (rotation)
    N->>A: requête API — Authorization: Bearer JWT
    A->>H: GET /api/auth/.well-known/jwks.json
(clé PUBLIQUE, mise en cache)
    Note over A: vérifie la signature en local
    A-->>N: 200 — données métier

L'app ne connaît jamais le mot de passe : elle ne voit que le JWT, qu'elle valide avec la clé publique du Hub (JWKS).

Le flux M2M — une app appelle une autre via le Hub

sequenceDiagram
    autonumber
    participant A as App A (Service Account)
    participant H as Hub (hub-api)
    participant B as App B (service partagé)
    A->>H: POST /api/auth/token (client_credentials)
    H-->>A: token M2M (identité SA)
    A->>H: GET /api/apps/discover
    H-->>A: catalogue — App B expose tel endpoint
    A->>B: appel M2M (Bearer token SA)
    B-->>A: réponse métier
    Note over A,B: échec après tous les retries
→ outbox : livraison garantie, retry auto

Les credentials SA sont chiffrés côté Hub (Fernet). Si l'app B est down, le message part en outbox et sera livré automatiquement.

2. Pilotage du parc avec hubctl

L'outil hubctl est le CLI/TUI d'administration transversal. Exécuté à la racine du parc, il gère le démarrage, la mise à jour, les secrets et la résilience.

Démarrage & Arrêt

Contrôle global des conteneurs via make et docker compose.

./hubctl start [all|prod|dev]
./hubctl stop [all|prod|dev]

Mise à jour sécurisée

Pull, rebuild et restart, avec snapshot BDD préalable et rollback auto.

./hubctl update

Le Coffre (Vault)

Archive Fernet+scrypt des .env et clés, synchronisée au kit PRA.

./hubctl vault status
./hubctl vault backup

Les 12 sous-commandes CLI

Exécutées à la racine du parc. Le flag global --dry-run (placé avant la sous-commande) simule sans exécuter.

CommandeEffet
start / stop [all|prod|dev]Cycle de vie du parc. dev = ateliers uniquement ; stop dev préserve les volumes.
updateMaj Hub + apps actives : snapshot DB préalable, pull → build → up, rollback automatique si échec.
atelier <app> [--maj [--ref R] | --prod]Cycle atelier blue-green (§7) : création avec clone DB, test de origin/main, déploiement validé.
init [--force]Bootstrap d'un Hub neuf : .env + secrets aléatoires, clés JWT, santé, marker shell.
export [--app S] [--passphrase-stdin]Archive chiffrée du parc complet (DB + .env + secrets), magic PARKEV1 → exports/.
restore <archive>Restaure un park-export — uniquement sur un Hub vierge.
pra-restore [kit]PRA sur machine nue : wizard en 7 étapes depuis le kit (§8).
debug [app] [--rw|--setup]Agent IA local de debug (Ollama + MCP hub-debug), coupé par --off.
vpn sync|status|on|offWireGuard : l'état voulu vit en DB, le conteneur est réconcilié par sync.
vault backup|restore|status|…Coffre chiffré Fernet+scrypt des .env/secrets (§8) + réplication PRA.
seed [fichier.yaml] [--prune]Déploiement déclaratif batch (clone/configure/converge) ; seed export génère le YAML.

Le TUI — un dashboard, pas un menu

./hubctl sans sous-commande (avec TTY) ouvre un dashboard 4 quadrants : bannière (version, mode DEV/PROD, badge PRA), ressources système, statut des services et apps, raccourcis.

Raccourcis mode PROD : 1 tout démarrer · 2 tout arrêter · 3 mise à jour · 4 Coffre · 0/Esc quitter. Mode DEV : 1/2 prod, 3/4 ateliers, 5 update, 6 Coffre. ⚠️ Depuis Hub 3.38.0, l'atelier se pilote aussi depuis l'UI Santé — ne pas lancer hubctl et l'UI simultanément sur la même app.

3. Cycle de vie d'une Application

Toute application naît d'une copie du HUBapp_TEMPLATE_base et s'intègre automatiquement au Hub. Le processus d'échafaudage est automatisé.

1. Scaffold Création depuis la racine

Le script valide le nom et copie le template sans son dossier .git.

scripts/create_app.sh mon-app

2. Personnalisation Script INITIALISE

S'exécute dans le dossier de l'app. Construit le .env, modifie les package.json et Dockerfiles, génère les scripts d'action.

cd APPS/mon-app
python INITIALISE.py --clean

3. Allocation Ports et Sous-réseau

L'app interroge le Hub central pour recevoir des ports uniques (ex: 9005 pour l'API) évitant toute collision Docker.

make sync-env

4. Démarrage Hot-reload ou Prod

Le développement quotidien utilise make dev pour profiter du Hot Module Replacement (HMR) sur React et Uvicorn reload sur FastAPI.

make dev # ou make up pour la prod

Prod vs atelier — des ressources étanches

Chaque app de production possède un jumeau d'atelier sur des plages dédiées : aucune collision possible, les deux peuvent tourner en parallèle.

4. Conventions Backend (FastAPI)

Le backend s'appuie sur FastAPI et valide la sécurité via les composants partagés du Hub. Le pattern standard utilise l'injection de dépendances pour les contrôles d'accès.

# backend/routes/mon_domaine.py from fastapi import APIRouter, Depends, HTTPException, status from ..hub_auth import get_current_user, require_role router = APIRouter(prefix="/api/items", tags=["Items"]) @router.post("/", status_code=status.HTTP_201_CREATED) async def create_item( data: ItemCreate, current_user=Depends(require_role("user")) # Exige le rôle user ou + ): # Validation via JWKS du hub transparente pass
Dépendance d'auth Accès requis
get_current_user() Tout token JWT valide (Utilisateur ou Service Account M2M)
require_role("viewer") Rôle Viewer minimum
require_role("admin") Administrateur d'application uniquement

Contrainte de temps (UTC Strict)

Il est interdit d'utiliser datetime.utcnow(). Utilisez toujours datetime.now(timezone.utc) dans le code Python et TIMESTAMPTZ dans PostgreSQL.

5. Base de données et Migrations

Les applications n'utilisent pas Alembic. Un script interne léger exécute des migrations SQL pures au démarrage du backend FastAPI.

Fichiers séquentiels

Placés dans backend/migrations/, ils sont nommés avec 3 chiffres : 001_init.sql, 002_add_field.sql.

BEGIN; CREATE TABLE IF NOT EXISTS projets ( id SERIAL PRIMARY KEY, titre VARCHAR(255) NOT NULL, proprietaire_id INTEGER NOT NULL REFERENCES users(id), created_at TIMESTAMPTZ NOT NULL DEFAULT NOW() ); COMMIT;

Le runner trace les exécutions dans la table schema_migrations. Chaque statement est isolé par un SAVEPOINT : un statement déjà appliqué (ex. colonne existante) est ignoré avec un warning, sans avorter le démarrage.

6. Référence Makefile (Apps)

Exécutées depuis le dossier de l'application (APPS/mon-app/), les commandes standardisent le cycle de développement.

CommandeEffet

make upDémarre les conteneurs de l'app en production.
make restart-apiRedémarre uniquement le conteneur FastAPI (rapide). ⚠️ Les dépendances pip sont bakées dans l'image : une nouvelle dépendance exige make build puis make up.

7. L'Atelier (Déploiement Blue-Green)

Pour tester une montée de version en sécurité sans casser la production, hubctl permet de générer un "Atelier".

Cycle de l'atelier

  1. ./hubctl atelier mon-app : Clône la Base de données en direct et assigne de nouveaux ports (ex: API sur 10005).
  2. ./hubctl atelier mon-app --maj : Pulle la nouvelle version origin/main dans cet espace isolé.
  3. Test fonctionnel sur l'URL de l'atelier.
  4. ./hubctl atelier mon-app --prod : Bascule le code vérifié en production et détruit l'atelier proprement.
flowchart TD
    P["PROD seule
(origin/main)"] -->|"atelier app"| W["ATELIER créé
clone DB + .workshop.env
ports 10000+ / subnet 10.210.x"]
    W -->|"atelier app --maj"| M["origin/main testé
itérativement sur le clone"]
    M -->|"tests OK"| S["atelier app --prod"]
    M -->|"échec"| RB["rollback git
atelier conservé (diagnostic)"]
    S -->|"garde anti-drift OK"| P2["PROD à jour
atelier supprimé"]
    S -->|"échec"| RB2["rollback prod + rebuild

    style P fill:#dcfce7,stroke:#16a34a

--prod exige que l'atelier ait testé exactement le commit courant d'origin/main (anti-drift). Échec = rien n'est perdu : rollback et atelier conservé. Depuis Hub 3.38.0, ce cycle est aussi pilotable depuis la vue Santé de l'UI admin.

8. PRA (Plan de Reprise d'Activité)

En cas de sinistre total de la machine hôte, POULIDOR est conçu pour se relever avec une commande unique, à condition d'avoir externalisé le kit.

Le Kit PRA

Contient l'archive du coffre (Fernet), la clé de déchiffrement, et le dernier snapshot système complet (tar.zst chiffré).

Doit résider hors du disque (Clé USB, NAS, etc.).

Restauration

Sur un serveur Linux nu avec Docker installé :

./hubctl pra-restore

Exécute un wizard en 7 étapes restaurant le Hub puis réinjectant chaque backup applicatif via API.

Sinistre — quel outil pour quelle situation ?
