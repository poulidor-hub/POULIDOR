Modes DEV et PROD

Objectif

Adapter le comportement de hubctl à ce qu'on est en train de faire : piloter la production, ou travailler sur un atelier (développement). Applications et ateliers vivent tous dans APPS/ : l'atelier d'une app est un 2ᵉ projet Docker Compose (-p X-ws) matérialisé par APPS/X/.workshop.env.

Détection du mode

Priorité aux flags explicites, puis auto-détection :

OrdreSourceEffet
1./hubctl --dev / ./hubctl --prodMode forcé pour la session.
2HUBCTL_MODE=dev / =prod (env)Mode forcé par l'environnement (scripts, cron).
3Auto-détectionDEV dès qu'une app de APPS/ possède un .workshop.env (atelier actif), PROD sinon.

Le mode courant est affiché dans le tableau de bord, et change les touches du menu (cf. guide hubctl) : en DEV, des entrées « Démarrer/Arrêter dev » apparaissent et le coffre passe en touche 6.

Pour travailler en DEV

On ne « bascule » plus : on crée simplement un atelier, et le mode suit.

  1. ./hubctl atelier X (ou depuis l'UI HUB, vue Santé) → .workshop.env créé.
  2. Relancer ./hubctl : mode DEV détecté, entrées dev disponibles.
  3. Fin du travail : déployer (--prod) ou supprimer l'atelier → retour auto en mode PROD.
⚠ Points d'attention
  • En DEV, les actions « dev » portent sur les ateliers (-ws), pas sur la prod — mais la prod reste démarrable et pilotable en parallèle.
  • Le clone atelier contient des données réelles : espace disque et confidentialité.
  • Supprimer .workshop.env à la main fait « sortir » du mode DEV sans arrêter les conteneurs de l'atelier : passez par hubctl ou l'UI.
En cas de problème

Le mode ne change pas alors qu'un atelier existe : vérifiez qu'aucun flag --dev/--prod ni HUBCTL_MODE ne force l'autre mode, et que le .workshop.env est bien dans APPS/<app>/.
