Atelier (workshop) : tester sans risque

Objectif

Travailler sur une app en bac à sable (atelier) avec une copie des données réelles, pendant que la prod continue de tourner. Une fois le code validé sur le clone, le déployer en production sans toucher à la base de données.

Modèle : 2ᵉ instance Compose à côté de la prod

L'atelier n'est pas une copie du dossier : c'est un 2ᵉ projet Docker Compose (-p X-ws) lancé depuis le même dossier APPS/X/, avec des variables d'override :

  • La prod APPS/X reste en place et tourne (ports et subnet distincts).
  • L'atelier a son propre slug (X-ws), ses ports alloués automatiquement (plages dédiées hubctl) et son subnet Docker dédié (pool 10.210.x) → zéro conflit avec la prod.
  • La DB est clonée dans un volume séparé (X-postgres-data → X-ws-postgres-data) : données réelles, manipulées sans danger.
  • L'état atelier est matérialisé par APPS/X/.workshop.env (7 clés : slug, ports, WS_REF/WS_COMMIT, subnet) — contrat partagé UI/CLI, ne pas éditer à la main.

Accès

Deux voies équivalentes (dualité assumée — hubctl reste l'outil de secours si l'UI HUB est down) :

  • UI HUB : Santé des Applications (admin) → carte de l'app → bloc atelier (créer / mettre à jour / déployer / supprimer), avec suivi de progression.
  • CLI : ./hubctl atelier <app> et ses flags.

Le cycle complet

ÉtapeCLIRôle
1. Créer./hubctl atelier XAlloue ports + subnet, clone la DB, build & up du projet -ws.
2. Mettre à jour./hubctl atelier X --maj [--ref <branche|tag>]git fetch + checkout (défaut main) + rebuild de l'atelier. Le ref/commit testé est tracé (WS_REF/WS_COMMIT).
3. Déployer en prod./hubctl atelier X --prodDéploie origin/main validé par l'atelier (le commit testé doit être le commit courant d'origin/main) : build + up + health check prod, puis suppression de l'atelier. DB prod préservée.
4. Supprimermenu atelier → supprimerdocker compose -p X-ws down -v + suppression de .workshop.env (ports et disque libérés).

Si l'atelier existe déjà, ./hubctl atelier X ouvre un menu à 4 choix : mettre à jour / déployer en prod / supprimer / annuler.

En coulisse (technique)

Création : lecture du .env prod, allocation de ports libres, choix d'un subnet libre, écriture de .workshop.env, clonage du volume DB via un conteneur Alpine (cp -a), puis docker compose -p X-ws build + up depuis APPS/X/. Échec de build → rollback (suppression config + volume).

Déploiement prod : garde HEAD == WS_COMMIT (ce qui part en prod est exactement ce que l'atelier a testé) → git pull → build → up → health check. Échec → rollback git (reset + rebuild) et atelier conservé pour diagnostic.

Le même cycle est pilotable depuis l'UI HUB (/api/apps/{slug}/workshop*, une opération à la fois, suivi en DB).

⚠ Points d'attention
  • Le clone recopie les données réelles de la base : traitez l'atelier avec le même soin que la prod.
  • Le slug de l'atelier est le slug de l'app suffixé -ws et normalisé (minuscules, _ → -, depuis hubctl 0.7.2) : ports et URL diffèrent de la prod.
  • --prod refuse de partir si origin/main a avancé depuis le test — relancez --maj puis redéployez.
  • Le down -v n'est légitime que pour détruire l'atelier (suppression ou ship réussi).
  • Ne supprimez jamais .workshop.env à la main sans faire le down -v correspondant (ports/subnet fantômes).
En cas de problème

Si une action échoue, l'app prod reste intacte (rollback git automatique, atelier conservé). Vérifiez l'espace disque et les ports libres, puis relancez. En dernier recours : supprimez l'atelier (down -v) et recréez-le.
