Workshop : atelier ↔ production

Objectif

Travailler sur une app en bac à sable (atelier) avec une copie des données réelles, sans impacter la production. Une fois le code prêt, le déployer en production sans toucher à la base de données.

Modèle : sandbox + deploy

Contrairement à l'ancien modèle « move » (déplacer physiquement les dossiers), le workshop fonctionne en sandbox parallèle :

  • La prod APPS/X reste en place (stoppée, jamais supprimée).
  • L'atelier APP_Workshop/X-ws est une copie indépendante (code + DB clonée).
  • « Shipper » = git pull sur la prod → la DB n'est jamais touchée par défaut.
  • La copie DB est l'exception explicite (--copy-db en CLI, jamais par défaut).

Accès

Disponible uniquement en mode DÉVELOPPEMENT :

  1. Menu principal → 5 pour basculer en mode DEV.
  2. Menu Apps (1) → Atelier (5).

Également accessible via Configuration (3) → Workshop.

Options du menu atelier

OptionRôle
[→] XMettre X en atelier (clone DB). Si X a des dépendances (🔗), propose automatiquement de les emmener aussi.
[←] X-wsDéployer le code vers la prod via git pull. DB prod préservée.
[×] X-wsSupprimer l'atelier (down -v + backup + redémarrage de la prod).
[→→]Multi-sélection : cocher plusieurs apps à mettre en atelier d'un coup. Les dépendances sont automatiquement incluses.
[→+]Ajouter une app à un atelier existant sans toucher au reste.

Dépendances inter-apps 🔗

Chaque app peut déclarer ses dépendances M2M via un fichier depends.yaml à sa racine :

depends_on:
  - slug: exemple-app-2
    note: "Catalogue articles"

Le menu atelier affiche un indicateur 🔗 et propose automatiquement d'emmener les dépendances quand on met une app en atelier. Si vous refusez, un warning vous alerte du risque de défaut M2M.

En ligne de commande

CommandeRôle
./hubctl work XMettre X en atelier.
./hubctl work X,Y,ZMulti-slug : mettre X, Y et Z en atelier en une passe.
./hubctl ship XDéployer le code vers la prod (git pull, DB préservée).
./hubctl ship X --copy-dbAvancé : écraser la DB prod (destructif, confirmation par saisie).
En coulisse (technique)

Mise en atelier : docker compose stop sur la prod (pas de down -v), copie du code vers APP_Workshop/X-ws, clone du volume Docker via un conteneur Alpine, réécriture du slug en -ws dans le .env, puis build + up. La prod reste en place, stoppée.

Déploiement : git pull sur la prod → build + up → health check. La DB n'est jamais touchée. --copy-db est l'exception qui clone le volume atelier → prod (avec backup préalable).

⚠ Points d'attention
  • Le mode DEV est obligatoire pour voir le menu Workshop.
  • Le clone recopie les données réelles de la base : traitez l'atelier avec le même soin.
  • Le slug change (-ws) : les ports et l'URL diffèrent de la prod.
  • --copy-db est destructif : jamais par défaut, confirmation explicite requise.
  • Le bouton [×] est le seul endroit où docker compose down -v est utilisé.
En cas de problème

Si une action échoue, l'app source reste intacte. Le déploiement code-only a un rollback automatique (git reset) si le health check échoue. Vérifiez l'espace disque (2 → Apps Vue+Disque) et relancez.
