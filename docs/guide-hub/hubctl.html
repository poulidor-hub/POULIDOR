Prendre en main hubctl

hubctl est le poste de pilotage du parc : un menu interactif lancé dans le terminal du serveur, complété par des sous-commandes non interactives pour les scripts.

Lancer l'outil

./hubctl                 # menu interactif (intro animée)
./hubctl --no-anim       # sans l'intro animée
./hubctl --dry-run       # affiche les commandes sans les exécuter
./hubctl --dev           # force le mode DÉVELOPPEMENT (atelier)
./hubctl --prod          # force le mode PRODUCTION
Mode auto-détecté Sans --dev/--prod, le mode est détecté automatiquement : DEV dès qu'une app de APPS/ possède un fichier .workshop.env (atelier actif), PROD sinon. On peut aussi forcer via la variable d'environnement HUBCTL_MODE=dev ou HUBCTL_MODE=prod.
Sans terminal interactif (pipe, cron, SSH non interactif), hubctl affiche simplement l'état du hub puis quitte — le menu requiert un vrai terminal (TTY). Utiliser les sous-commandes CLI ci-dessous.

Le tableau de bord affiche en permanence l'état des services, le disque, les apps (version, git, statut) et une alerte ⚠ PRA si l'emplacement de secours est absent ou non synchronisé depuis 7+ jours.

Sous-commandes CLI (non interactives)

hubctl [-h] [--no-anim] [--dry-run] [--dev | --prod]
       {start,stop,update,atelier,init,export,restore,pra-restore,
        debug,vpn,vault,jwt,seed,socle}

--dry-run est un flag global : il se place avant la sous-commande (./hubctl --dry-run atelier X --maj).

Pilotage quotidien

CommandeRôle
./hubctl start [all|prod|dev]Démarre la stack (défaut : all).
./hubctl stop [all|prod|dev]Arrête toutes les apps et le Hub.
./hubctl update <cible…>Mise à jour ciblée : hub (Hub seul), un ou plusieurs slugs d'app, * ou all = Hub et toutes les apps. git pull + rebuild + health check + rollback. Sans cible : usage uniquement, rien n'est exécuté (quoter le * : "*").
./hubctl init [--force]Bootstrap automatique du Hub : génère le .env, démarre, vérifie la santé.

Atelier (workshop)

CommandeRôle
./hubctl atelier <app>Crée l'atelier de l'app ; s'il existe déjà, ouvre un menu (mettre à jour / déployer en prod / supprimer / annuler).
./hubctl atelier <app> --majMet à jour l'atelier : git fetch + checkout + rebuild du projet -ws (défaut : main).
./hubctl atelier <app> --maj --ref <branche|tag>Teste une branche ou un tag précis.
./hubctl atelier <app> --prodDéploie origin/main validé en prod, puis supprime l'atelier.
Depuis l'UI HUB (Hub 3.50.6) — la vue Santé des Applications embarque un panneau branches 🌿 : un admin peut envoyer n'importe quelle branche GitHub en atelier (création ou mise à jour). Garde-fou intact : le déploiement prod reste verrouillé sur origin/main — une branche n'atteint la prod qu'après merge. Un admin peut aussi activer par utilisateur la visibilité de l'atelier (checkbox « Atelier » de la modale des droits, Hub 3.48.3), indépendamment du rôle sur la prod.
Anciennes commandes disparues — work, ship, deploy, le multi-slug et --copy-db n'existent plus : tout le cycle est porté par atelier et ses flags.

Sauvegarde / restauration du parc (PRA)

CommandeRôle
./hubctl export [--app <slug>]Archive tout le parc (ou une seule app) dans un tar.gz chiffré par passphrase.
./hubctl export --no-encryptArchive non chiffrée (legacy, secrets en clair).
./hubctl export --passphrase-stdinLit la passphrase sur stdin (CI / DR).
./hubctl restore <archive>Restaure le parc depuis une archive — uniquement sur un Hub vierge.
./hubctl pra-restore [kit]Assistant de restauration PRA depuis un kit (coffre + dernier snapshot), scan auto du kit. Fanions : --snapshot, --apps all|none|a,b, --admin-user, --yes, --force, --dry-run.

Trousseau JWT

Gestion des clés de signature des tokens du Hub (depuis hubctl 0.10.x). La rotation se fait en overlap 24 h : l'ancienne clé reste utilisable pour la vérification pendant que la nouvelle signe.

CommandeRôle
./hubctl jwt keysLister le trousseau (kids, statut, dates).
./hubctl jwt rotateRotater la clé de signature (overlap 24 h).
./hubctl jwt revoke --kid <kid>Révoquer une clé (mode compromission).
./hubctl jwt cleanupSupprimer les PEM archivés/révoqués anciens.

Seed & debug IA

CommandeRôle
./hubctl seed <fichier.yaml>Déploie/converge les apps décrites par un fichier seed. --prune supprime les apps non listées, --dry-run simule.
./hubctl seed export [-o <fichier>] [--force]Exporte l'état du parc vers un seed YAML (défaut : seed-export-YYYY-MM-DD.yaml).

Socle (HUBsocle)

Les nouvelles apps naissent sur un socle applicatif versionné (sous-module HUBsocle/, paquets hub-socle / @poulidor/hub-socle, images de base poulidor/socle-api et poulidor/socle-web). Chaque app déclare la version du socle utilisée via APP_SOCLE_VERSION dans son .env.

CommandeRôle
./hubctl socle build [--force]Construit localement les images de base du socle depuis le checkout HUBsocle/ (tag poulidor/socle-api:<VERSION> / socle-web:<VERSION>, cache par tag, offline-first : aucun registre requis). --force rebâtit même si le tag existe.
./hubctl socle statusTableau de drift de la flotte : version du socle déclarée par chaque app vs version du sous-module (« à jour », « en retard », « fork template » si la variable n'est pas déclarée).
Les apps existantes (forks du template) ne sont pas concernées ; le pilote du socle est exemple-app. Les futures apps naîtront « fines » via INITIALISE v2 (à venir).

Le tableau de bord (TUI)

Le menu interactif est un tableau de bord à accès direct : on tape directement la touche de l'action souhaitée (1…6, 0 pour quitter — voir table du menu ci-dessus), pas de navigation ↑/↓ entre des entrées. Ctrl+C interrompt l'action en cours et revient au tableau de bord.

Les garde-fous

hubctl vous protège
  • Chaque action destructrice demande une confirmation Oui/Non (jamais de saisie libre).
  • Une app supprimée part en corbeille (hubctl_src/hubctl_cli/_trash/), jamais un rm -rf.
  • Une archive tar.gz est créée avant toute suppression.
  • atelier --prod exige que l'atelier ait testé main au commit courant d'origin/main ; rollback git automatique en cas d'échec, atelier conservé si le déploiement prod échoue.
  • Garde disque : avertissement sous 15 % d'espace libre, refus sous 5 %.
  • --dry-run global pour simuler sans risque.
En coulisse (technique)

Les opérations s'appuient sur les Makefile du parc : make -C HUB_base … pour le hub central et make -C APPS/<nom> … pour les apps — y compris l'atelier, qui tourne dans le même dossier via un 2ᵉ projet Docker Compose (-p <app>-ws) piloté par APPS/<app>/.workshop.env. Au premier lancement, le launcher crée l'environnement Python (hubctl_src/hubctl_cli/.venv) et installe les dépendances (rich, cryptography, mcp, pyyaml). Sans terminal interactif, il affiche l'état du hub puis quitte.
