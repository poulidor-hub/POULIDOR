Prendre en main hubctl

hubctl est le poste de pilotage du parc : un menu interactif lancé dans le terminal du serveur.

Lancer l'outil

./hubctl                 # menu interactif (avec intro animée)
./hubctl --no-anim        # sans l'intro animée
./hubctl --anim random    # choisit une animation d'intro au hasard
./hubctl --dry-run        # affiche les commandes sans les exécuter
./hubctl --init           # clone les dépôts manquants du parc
./hubctl --dev            # force le mode DÉVELOPPEMENT (APP_Workshop/)
./hubctl --prod           # force le mode PRODUCTION (APPS/)
Astuce --dry-run est idéal pour découvrir sans risque : rien n'est réellement exécuté.
Sans terminal interactif (pipe, cron, SSH non interactif), hubctl affiche simplement l'état du hub puis quitte — le menu requiert un vrai terminal (TTY). On peut aussi forcer le mode via la variable d'environnement HUBCTL_MODE=dev ou HUBCTL_MODE=prod.

Sous-commandes CLI (non interactives)

Piloter le parc depuis un script ou sans entrer dans le menu. Toutes ces commandes sont non interactives (sauf ship) et peuvent être automatisées.

Pilotage quotidien

CommandeRôle
./hubctl statusVue d'ensemble texte du parc (Hub + apps + mode courant).
./hubctl start hubDémarre le hub central.
./hubctl start <slug>Démarre une app.
./hubctl stop hubArrête le hub central.
./hubctl stop <slug>Arrête une app.
./hubctl update hubMet à jour le hub : stop → git pull → build → up → health check, avec rollback automatique (git reset + restauration DB) si la santé ne revient pas.
./hubctl update <slug>Idem pour une app (sans snapshot DB).
./hubctl deploy hubDéploiement blue-green (zéro downtime) : instance verte sur ports+1 → health check → swap. --validate pour validation humaine avant swap.
./hubctl deploy <slug>Idem pour une app.
./hubctl work <slug>Met une app en atelier : copie code + volume DB vers APP_Workshop/<slug>-ws et démarre.
./hubctl ship <slug>Ramène une app de l'atelier vers la prod. ⚠ Remplace la DB de prod par celle de l'atelier (confirmation : retaper le slug).

Sauvegarde / restauration du parc

CommandeRôle
./hubctl park-exportArchive tout le parc (Hub + apps) dans un tar.gz chiffré par passphrase.
./hubctl park-export --app <slug>Archive une seule app.
./hubctl park-export --no-encryptArchive non chiffrée (legacy, secrets en clair).
./hubctl park-export --passphrase-stdinLit la passphrase sur stdin (CI / reprise après sinistre).
./hubctl park-restore <archive>Restaure le parc depuis une archive — uniquement sur un Hub vierge.
./hubctl park-restore <archive> --passphrase-stdinRestauration automatisée (passphrase via stdin).

Dev (cibles granulaires)

CommandeRôle

Les garde-fous

hubctl vous protège
  • Chaque action destructrice demande une confirmation Oui/Non.
  • Une app supprimée part en corbeille (hubctl_cli/_trash/), jamais un rm -rf.
  • Une archive tar.gz est créée avant toute suppression.
  • update capture le commit git courant + un snapshot DB (pour le hub) et rollback automatique (git reset + restauration DB) si le health check échoue.
  • ship <slug> demande de retaper le slug pour confirmer le remplacement de la DB de production.
  • Garde disque : avertissement sous 15 % d'espace libre, refus sous 5 %.
En coulisse (technique)

Les opérations s'appuient sur les Makefile du parc : make -C HUB_base … pour le hub central et make -C APPS/<nom> … pour les apps. Au premier lancement, hubctl crée un environnement Python (hubctl_cli/.venv) et installe rich et cryptography. Sans terminal interactif (pipe, cron), il affiche l'état du hub puis quitte.
