Ajouter une application

Objectif

Deux situations, deux outils — ne pas les confondre :

  • Installer une application existante (mise en service client, exploitation) : l'app vit dans son dépôt git, on la dépose dans le parc avec ./hubctl app install <url-git>.
  • Créer une nouvelle application (développement) : l'app naît du template ou du socle, puis se déploie comme ci-dessus.

Installer une application existante

La voie reine, une seule commande :

./hubctl app install https://github.com/mon-org/mon-app.git

Ce que fait app install, dans l'ordre :

  1. clone du dépôt dans APPS/<nom-du-dépôt> ;
  2. installation des dépendances déclarées dans depends.yaml (leur URL est résolue dans le registre du Hub ; une dépendance absente du registre n'empêche pas l'installation — simple avertissement) ;
  3. génération du .env — secrets par défaut neutralisés, rien de réutilisé d'une autre app ;
  4. garantie des images du socle (hubctl socle build si nécessaire) ;
  5. allocation des ports auprès du Hub (make sync-env), puis make build ;
  6. pré-création de l'app dans le registre du Hub, approvée quand le jeton admin est disponible ;
  7. démarrage (make up) et health check ;
  8. certificat signé par la CA du Hub, synchronisation du coffre, puis rapport final (code de sortie 0 seulement si toutes les apps répondent).
Options --no-deps : ignorer les dépendances déclarées (depends.yaml) — avec avertissement. --yes : aucune confirmation (comportement effectif sans terminal interactif). On peut aussi passer un fichier seed en argument unique : ./hubctl app install apps.yaml.
Approbation Le mot de passe admin est pris dans HUBCTL_ADMIN_PASSWORD, sinon ADMIN_PASSWORD de HUB_base/.env, sinon demandé à l'écran (saisie masquée). Sans jeton, l'installation continue quand même : l'app reste « En attente » dans le Hub, il faut l'approuver depuis l'UI — Administration → Applications → Approuver.
Certificat et navigateur Le HTTPS des apps s'appuie sur la CA du Hub. Pour supprimer l'avertissement navigateur sur les postes clients, installez le certificat racine : https://<IP-du-serveur>/api/pki/ca.crt.

Déployer une flotte

Pour plusieurs apps d'un coup, ou pour converger le parc vers une liste connue :

./hubctl seed apps.yaml          # déploie ou converge les apps listées
./hubctl seed apps.yaml --dry-run   # simuler d'abord

Le fichier seed est une simple liste d'URLs git — le slug est déduit du nom de chaque dépôt :

apps:
  - https://github.com/mon-org/mon-app.git
  - https://github.com/mon-org/mon-autre-app.git

--prune supprime les apps présentes mais non listées (confirmation globale), ./hubctl seed export écrit un seed depuis l'état du parc. C'est un outil de convergence de flotte : pour la première installation d'une app, passer par hubctl app install.

Créer une nouvelle application (développeur)

Trois points de départ, au choix :

  • Template canonique : bash scripts/create_app.sh <nom> copie HUBapp_TEMPLATE_base dans APPS/<nom>, puis python3 INITIALISE.py depuis le dossier de l'app personnalise et finalise l'installation locale.
  • Socle applicatif (apps « fines ») : python3 HUBsocle/INITIALISE.py --name "Mon App" --slug mon-app génère une app adossée au socle versionné (HUBsocle/).
  • Assistant IA : demander à l'agent (« Crée une app … ») — le skill create-hub-app orchestre toute la création.

Une fois l'app poussée dans son dépôt git, elle s'installe sur un serveur comme toute app du parc : hubctl app install <url> ou seed.

En cas de problème

⚠ Points d'attention
  • Vérifiez l'espace disque avant d'installer : garde hubctl — avertissement sous 15 % libre, refus sous 5 %.
  • L'app reste « En attente » dans le Hub ? Approuvez-la depuis l'UI (Administration → Applications → Approuver) ou relancez avec HUBCTL_ADMIN_PASSWORD.
  • Avertissement navigateur sur l'app ? Installez le certificat racine du Hub (/api/pki/ca.crt) sur les postes clients.
  • Le rapport final d'app install nomme l'étape qui a échoué ; le code de sortie dit si toutes les apps répondent.
En coulisse (technique)

app install s'appuie sur les Makefile du parc : make sync-env (ports alloués par le Hub), make build, make up, health check. L'app est pré-créée au registre du Hub via l'API admin (avec son Service Account) ; le jeton admin est lu dans HUBCTL_ADMIN_PASSWORD ou ADMIN_PASSWORD (HUB_base/.env). Le seed, lui, converge le parc : apps installées dans APPS/ mais absentes du fichier = candidates au retrait avec --prune.
