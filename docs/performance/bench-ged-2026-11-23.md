# Benchmark GED v0.4.0 — validation réelle & stress

**Date** : 23 novembre 2026 · **Labo** : VM Debian 12 `ged-perf` (4 vCPU / 8 Go / KVM, overlay 60 Go)
**Déploiement testé** : installation **type client** de bout en bout — méta `fd93ef4` → `install.sh` (Hub 3.100.1) → GED **v0.4.0** (socle 2.38.0, backend Rust axum + sqlx + hub-client 0.1.0) auto-enregistrée (`hub_connected: true`), 4 conteneurs healthy (api, frontend, postgres, meilisearch — aucun port public Meili).
**Données** : 100 % synthétiques (seed 42, skill data-generate voie A) — 15 238 documents texte (30–150 Ko, contenus uniques), 130 scans image (OCR tesseract réel), gros fichiers 1–50 Mo.
**Limites du lab** : exemple-app et exemple-app-11 absents → uploads « généraux » et partage externe testés **en dégradation** (comportements fail-closed validés : 422/503 propres, jamais 500). Valeurs absolues VM-flavored — lire surtout les *tendances*.

## Méthodologie

- **Chargement** : uploads API parallèles (batchs de 10 fichiers, c=8) ; générateur de charge maison en Python (threads, mix de requêtes configurables, tokens pré-mintés — le login Hub est rate-limité 5/60 s/IP, JWT valables 8 h).
- **Mesures** : percentiles p50/p90/p95/p99 sur durées de 30–60 s par point, connexions sans keepalive ; sampler `docker stats` + file `jobs` + tailles DB/stockage toutes les 15 s.
- **Worker** : `GED_WORKER_POLL_MS=100` (voir Finding-03 — le défaut est 2 000 ms).
- **Idempotence** : plages de fichiers fraîches par palier (jamais de collision SHA-256 dans les mesures).

## Phase 2 — Stress & limites

### S1 — Volume (5k → 10k → 15k documents)

Charge recherche/listes c=10, 30 s par point :

| Palier | search rps | search p95 | list rps | list p95 | DB | stockage | Meili RAM |
|---|---|---|---|---|---|---|---|
| ~5 000 | 733 | 24,0 ms | 346 | 51,5 ms | 21 Mo | 463 Mo | ~232-299 MiB |
| ~10 000 | 747 | 24,3 ms | 202 * | 82,1 ms * | 34 Mo | 932 Mo | 214 MiB |
| ~15 000 | 691 | 27,7 ms | 141 | 113,1 ms | 46 Mo | 1 401 Mo | 223 MiB |

\* mesure 10k prise juste après le drain massif (checkpoint/vacuum en cours) — tendance fiable : la **recherche plein-texte est plate de 5k à 15k** (Meili), la **liste paginée SQL dégrade ~×2,2 sur le p95** entre 5k et 15k (OFFSET + tri).

**Rebuild d'index global** (admin) : **461 ms @5k → 2 109 ms @15k** (push par lots de 500).
**Ingestion** : uploads 500–710 docs/s (47–68 Mo/s, ko=0 sur plages fraîches) ; traitement worker ≈ **5–6 docs/s** (2 jobs/doc : extract+sync, claim séquentiel).

### S3 — Charge recherche/listes à 15k documents (60 s par point)

| Concurrence | search rps | search p95 | list rps | list p95 | Erreurs |
|---|---|---|---|---|---|
| 10 | 588 | 29,2 ms | — | — | 0 |
| 50 | 619 | 133 ms | 147 | 398 ms | 0 |
| 100 | 619 | 278 ms | 144 | 776 ms | 0 |
| **200** | **608** | **483 ms** | — | — | **0** |

- **Plateau de débit recherche ≈ 600–620 rps** quel que soit c — la latence absorbe la file (p95 29 ms → 483 ms de c=10 à c=200), **zéro erreur jusqu'à c=200** : pas de knee brutal, écrêtement progressif.
- **Listes** saturent ~145 rps (SQL) — p95 double entre c=50 et c=100.
- **Repli dégradé** (Meili arrêté, search c=50) : **80,5 rps, p95 721 ms, 200 OK partout** — ≈ ×7,7 plus lent que Meili mais le service reste rendu, conformément au design (« jamais de 500 »).

### S4 — OCR burst (60 scans image, uploads c=5)

- Ingestion : 60 scans (~470 Ko) à 182 docs/s (85,4 Mo/s) ; **traitement worker : 282 s ≈ 12,8 scans/min** (tesseract fra, mono-worker).
- CPU conteneur api : pics **~300 %** (multi-cœur), RAM api ≤ 385 Mo ; Meili au repos pendant l'OCR (31 Mo) ; postgres stable (~120 Mo).
- **Contenu OCR indexé vérifié** : `q=SCAN-42-010` → trouvé, `degraded:false` (le texte OCRed est bien recherchable).

### S5 — Charge mixte (knee d'utilisation réelle)

Mix 35 % recherche / 30 % listes / 15 % détail / 15 % download / 5 % uploads uniques (~13 dépôts/s à c=10), 45 s par niveau, 15 358 docs :

| Concurrence | rps | p50 | p95 | p99 | Erreurs |
|---|---|---|---|---|---|
| 10 | 272 | 11 ms | 125 ms | 165 ms | 0 |
| 25 | 114 | 139 ms | 615 ms | 1,02 s | 0 |
| 50 | 121 | 259 ms | 999 ms | 1,70 s | 0 |
| 75 | 130 | 375 ms | 1 372 ms | 2,39 s | 0 |
| 100 | 276 | 392 ms | 694 ms | 969 ms | 0 |
| 150 | 279 | 594 ms | 965 ms | 1,44 s | 0 |
| **200** | **274** | **809 ms** | **1 327 ms** | **1,95 s** | **0** |

- **Aucun knee brutal : 0 erreur jusqu'à 200 utilisateurs mixtes simultanés** (dont ~13 uploads/s), la latence se dégrade progressivement (p50 ×73, p95 ×10 entre c=10 et c=200).
- Creux de débit dans la bande c=25–75 (~115–130 rps) puis récupération ~275 rps à c≥100 : les uploads de la charge génèrent en continu des jobs extract+sync que le worker mono-thread digère en tâche de fond — la bande médiane coïncide avec les phases de checkpoint/vacuum Postgres ; la variance inter-paliers (>×2) est à lire comme bruit de fond worker+DB, pas comme instabilité serveur.
- En utilisation réelle (~20–50 utilisateurs simultanés), la GED opère avec p95 < 1,4 s dans le pire mix, et < 130 ms hors contention worker.

## Découvertes (issues de la campagne)

| # | Sévérité | Constat | Recommandation |
|---|---|---|---|
| **BUG-01** | Moyenne | Un `type_code` contenant un underscore est **accepté à la création** (`POST /api/document-types`) mais **refusé au stockage** (confinement G13) → tout upload de ce type échoue 422 « Chemin hors du répertoire de stockage » | Valider le charset du code à la création du type (même règle que le composant de chemin) |
| **FINDING-02** | Info perf | Ingestion worker = **1 job claimé par poll** (`FOR UPDATE SKIP LOCKED` + sleep) → débit borné par `GED_WORKER_POLL_MS` : défaut 2 000 ms ≈ 0,5 job/s ; 100 ms ≈ 5–6 docs/s | Pour de gros dépôts initiaux : tuner le poll, ou batch-claimer N jobs |
| **FINDING-03** | Faible | `GED_WORKER_POLL_MS` est documenté dans `.env.example` mais **absent de la section `environment` du `docker-compose.yml`** → le knob est inerte en l'état (patch lab requis pour le test) | Ajouter `- GED_WORKER_POLL_MS=${GED_WORKER_POLL_MS:-2000}` au service api |
| **Divers** | Faible | `install.sh` : timeout interne 120 s sur le premier build/démarrage Hub (dette harness connue — conteneurs healthy juste après) ; routes GET avec query string → 307 trailing-slash FastAPI (clients non-suiveurs de redirection voient un corps vide) | Augmenter le timeout du step Hub ; documenter `curl -L` côté intégrateurs |

## Limites du test & recommandations

- Le repli SQL dégradé est **fonctionnel mais 7,7× plus lent** — surveiller Meilisearch en prod (le health de l'app ne le couvre pas explicitement).
- La liste paginée (OFFSET) dégrade avec le volume (p95 ×2,2 entre 5k et 15k) — au-delà de ~50k docs, envisager une pagination keyset (curseur `created_at,id`).
- L'OCR reste mono-worker (~13 scans/min) — un pool de N workers (le claim `SKIP LOCKED` y est déjà prêt) multiplierait le débit d'ingestion des scans.
- `hub_connected` ne garantit que l'app ; un watch extérieur sur Meili (port interne) compléterait la supervision.
